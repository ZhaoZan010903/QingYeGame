## 4 本地启动与构建

使用Node及pnpm，前端依赖以各项目 `pnpm-lock.yaml` 为准；本轮Go构建使用1.27.4，代码最低版本以go.mod为准。构建、测试、vet和扫描使用一致的 `nomsgpack` 标签。两个前端分别安装，不共用单一应用入口。

```sh
cd 代码/前端/用户端
pnpm install --frozen-lockfile
pnpm test
pnpm build

cd ../管理端
pnpm install --frozen-lockfile
pnpm test
pnpm build

cd ../../后端
go test -tags=nomsgpack ./...
go vet -tags=nomsgpack ./...
go build -tags=nomsgpack ./cmd/qingye
```

Windows也可在对应工作目录分开执行以上命令。不要把Linux的环境变量语法直接复制进PowerShell。

用户端构建 `VITE_DATA_MODE=api`、`VITE_API_BASE_URL=/api/v1`、`VITE_SMS_ENABLED=false`；演示模式不得用于当前测试部署。管理端使用自己的 `.env.example`，所有 `VITE_` 变量均公开可见，禁止放密钥。

后端从仓库外的环境文件读取DATABASE_URL、REDIS_URL、SESSION_SECRET和MEDIA_DIR。`APP_SURFACE=public/admin` 决定路由和会话入口。执行 `migrate` 后可用 `seed-user` 从标准输入创建测试用户；不要把密码放进命令行参数。详情见后端双语README。

`go test` 在未提供测试数据库/Redis时可能跳过集成测试，不能据此宣称真实数据库验证完成。实际回归需设置 `TEST_DATABASE_URL` 与测试Redis，检查日志中没有预期集成项被跳过；每轮使用隔离schema和清理逻辑。

## 7 关键业务和易错点

- 公开商品须published、approved_version等于version且分类启用。已展示商品修改后退出公开展示，复审后再发布。
- 图片分页携带版本，409需重新取得完整商品后重建图集，不能将新图和旧价格混合；慢分页回调不能覆盖用户后来的选择。
- 旧业务编号存在两组重复，按唯一legacy_id迁移，不按编号去重。旧等级可能是中文字符串，不能强转Number导致NaN。
- 旧原图URL有字面百分号：只在原编码请求400时使用兼容编码，存储键仍以原始URL计算；不修改原始映射。
- 热门采用7个北京时间自然日的浏览/收藏加权批次；所有来源商品都不加新品分。业务事实、去重和重算锁在PostgreSQL，Redis当前不缓存完整商品列表。
- 图集总量无限制不等于单文件或单批无限制；保持大小/像素/类型校验和解码并发限制。

## 8 发布和恢复

先在隔离环境执行 `acceptance_suite.py` 的functional→concurrency→security，使用同一轮state文件。脚本拒绝5178—5182业务目标，不能删除限制来灌入测试数据。发布新的版本目录，核对SHA256和Nginx配置，再切换current；保留上一版本及DB备份。

回退应用不能直接覆盖数据库；schema变更和媒体迁移分别处理。备份脚本会新建临时恢复库，只删除本次创建的库；目前恢复证据是指定表数量和旧商品摘要比对，不等于逐字段全库或异地原图恢复验证。

GitHub仅保存代码、依赖锁、脱敏报告和文档。原图、真实快照、账号、Cookie、数据库导出、日志、dist和node_modules均不提交。更新使用正常快进或带expected SHA的引用更新，不强推。
