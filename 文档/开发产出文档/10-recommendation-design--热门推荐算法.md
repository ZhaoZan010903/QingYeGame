# 推荐算法与统计口径

## 1 当前实现

联调后端采用可解释的近7个北京时间自然日加权热度榜，并保留独立的人工精选和最新发布分区。它使用本站实际浏览、收藏及可确认的首次公开时间；没有机器学习训练、用户画像、成交推断或付费推广。

按分数维护榜单、按日或周聚合窗口是常见实现方式，[Redis官方排行榜说明](https://redis.io/docs/latest/develop/use-cases/leaderboard/)介绍了这类结构及窗口组合。本项目目前只有数百商品，以 PostgreSQL 保存行为事实和完整计算快照；Redis承担限流及可重建的批次指针，不把 Redis 缓存当成权限依据。

[Elasticsearch官方评分说明](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-function-score-query)提供加权组合及线性、指数、高斯衰减。这里选择自然日窗口淘汰旧行为，暂不按商品年龄连续衰减：旧账号仍可能持续获得真实关注，不能仅因创建较早被长期降权。这是依据本项目业务作出的选择，并非这些资料证明当前权重已经最优。

## 2 公式及可编辑参数

```text
热度 = V × view_weight + F × favorite_weight + N

V：窗口内按“商品、访客、北京时间日期”去重的有效浏览数
F：首次收藏位于窗口内、当前仍有效的会员人数
N：可确认首次公开时间且未满 new_hours 的新品加分，否则为0
```

| 字段 | 默认值 | 允许范围与含义 |
| --- | --- | --- |
| version | integration-v1 | 非空、最多40字节的可读版本标识。 |
| window_days | 7 | 1–30个北京时间自然日，包含计算当天。 |
| view_weight | 1 | 0–100，每次有效日浏览的权重。 |
| favorite_weight | 5 | 0–100，每位窗口内首次收藏会员的权重。 |
| new_bonus | 10 | 0–100，新品加分。 |
| new_hours | 72 | 1–720小时，新品加分时限。 |

配置键为 `recommendation`，只允许管理员维护。保存配置不会立即改写已完成的分数；下一次定时或手动刷新后生效。批次同时保存实际采用的配置、版本及截止时刻，失败则保留上一批完整结果。权重是运营可调整的起点，尚未经过本站转化数据验证。

## 3 时间和重复行为

同一批只使用一个截止时刻和一个数据库一致性视图。例如北京时间1月2日零点计算7天榜，窗口从12月27日零点开始，到该计算时刻截止。最早一天包含边界，未来日期及截止时刻之后的记录不参与。

| 行为 | 计数规则 |
| --- | --- |
| 游客浏览 | 服务端签发并签名匿名 Cookie；同商品、同访客、同北京时间日期只记一次。 |
| 已登录浏览 | 按会员 ID 去重，同一会员更换登录会话不增加当天计数。 |
| 本人商品、后台预览 | 不计浏览。管理接口不提供行为上报入口。 |
| 重复刷新、网络重试 | 数据库唯一键阻止重复累加，接口重复时返回 recorded:false。 |
| 收藏、取消、再次收藏 | 恢复同一条关系，不修改首次收藏时间；旧收藏不会通过反复操作变成新收藏。 |
| 新品边界 | 首次公开时间不晚于计算时刻，且严格未满配置小时数才加分；恰好72小时不加分。 |
| 重新上架、复审 | 保留原首次公开时间，不重新领取新品加分。 |

浏览有 Redis 频率限制，客户端不能指定访客签名、行为日期或累计次数。匿名访客清除 Cookie 或切换设备仍可能被计为不同访客；它是受约束的近似行为信号，不是精准自然人识别。

本版新增 `product_views_daily.created_at` 以处理精确截止。已有日统计的原日期不改变，缺失的写入时刻按迁移时刻回填；不能把该回填值解释为旧行为的真实发生时刻。

## 4 导入数据

旧站 `create_time` 只证明原记录的创建时间，不能直接证明首次公开。因此 `source=legacy` 的商品默认不领取新品 N。原时间继续用于稳定的“最新”顺序，并明确其来源依据；导入时间不会替代原时间。

旧商品可以凭本站新产生的真实浏览 V 和收藏 F 进入热门。原报价、分类和完整标题保持来源值；2026年11月11日确认的出售元、时日元/日、周月元/月另回填业务报价，只有同单位有效金额参与价格比较。价格及单位回填不修改首次发布时间，不产生新品加分。图片数量、原价格、上传次数、客服二维码打开次数均不增加热度。

## 5 次序、候选和冷启动

排序为：热度降序 → 原有首次公开 / 导入创建时间降序，未知时间最后 → 唯一商品 ID 升序。重复业务编号不会导致商品丢失，也不会使同分排序不确定。

候选始终要求商品已展示、当前版本已审核、分类启用。普通列表先按分类及筛选条件确定候选，再排序；它不会只筛一小段全站榜单。草稿、下架、撤回和停用分类立即被数据库条件排除，无需等待下一批计算。下一批还会清除这些商品的派生分数。

尚无行为数据时使用新品加分和稳定的时间次序补位，不产生虚构浏览或收藏。没有快照或快照超过60分钟未成功更新时，热门顺序回退到最新排序。首页响应带 `recommendation_source` 说明是否使用真实行为分数，界面不展示虚构热度数字。

首页先排人工精选，再按 `home_presentation.sections` 的配置顺序安排热门 / 最新，各区去重并遵守配置数量；库存不足时自然减少，不复制商品填满。人工精选顺序不写入自然热度。

## 6 计算与读请求

公开 API 进程每15分钟执行一次刷新；管理 API 不重复启动定时任务，可手动调用同一刷新逻辑。数据库事务互斥锁避免同批竞争，`RepeatableRead` 保证统计读到同一视图，分数和批次元数据原子提交。Redis批次指针可重建，Redis故障不改变已保存分数；浏览和登录依赖的限流不可用时明确返回错误。

目录与首页按当前数据库可见性读取。没有缓存整页商品响应，避免下架或权限变化后仍暴露旧内容。当前规模下完整目录分页查询为毫秒级；后续只有数据量和实测需要时才增加分数索引缓存，且仍需逐次验证公开条件。

## 7 验证证据

`代码/后端/internal/app/recommendations_integration_test.go` 使用独立 PostgreSQL schema 和测试 Redis，覆盖：

- 跨年及北京时间午夜的自然日窗口、首尾边界、未来日期与同日未来时刻。
- 新品恰好到期、未满时限、未来公开时间和 legacy 数据来源。
- 同输入重复计算、参数保存后尚未生效、刷新后生效及失败批次回滚。
- 同分次序、未知时间、无行为冷启动、陈旧分数回退、重复业务编号。
- 首页配置顺序和去重、即时下架 / 分类停用、空候选清除旧分数。
- 游客重复、同会员多个会话、本人浏览、后台上报、重复收藏及重上架日期。
- 公开列表省略重复介绍，详情和精选仍保留完整介绍与标题。
