# R23 界面排版与推荐加分设计

更新日期：2026年11月14日。本文记录当前工作区的 R23 实施设计，源基线为 `2c64e11221739b4ab3051f7e53bcb9375055c9e1`。前端本地验证、后端隔离测试、HTTP三阶段及真实隔离管理浏览器14组已通过，最终布局复测与业务测试环境发布尚待完成；本文不表示业务测试站已经切换。最终证据见[本轮验收记录](../业务验收与审查记录/UI-R23--界面排版与推荐加分验收.md)。

## 1 范围与业务边界

| 项目 | 本轮行为 |
| --- | --- |
| 电脑搜索框 | 扩大集市主搜索与导航停靠搜索，统一搜索提示，保留原查询和动画行为 |
| 商品表单 | 管理端按会员发布顺序整理字段；出售隐藏交易分类，租赁标签移入账号资料 |
| 商品管理列表 | 商品编号成为独立首列，手机卡片中也优先显示 |
| 推荐加分 | 管理员为单商品设置 0—100 整数加分，使用独立接口与版本 |
| 管理端排版 | 提高辅助文字可读性，调整列表、表单和操作栏的小屏布局 |
| 看板审核事项 | 突出当前全部待审核商品和昵称数量，保留既有审核入口及统计口径 |

会员发布原本已无交易分类选择框，本轮不重复增加或修改该控件。商品公开资格、审核流程、多租期报价、图片生命周期、昵称审核和管理员权限边界继续按现行规则执行。推荐加分不是上架入口，不使草稿、待审、删除或停用分类中的商品进入公开列表。

## 2 搜索框与响应式布局

原导航搜索高度为 37px、最大宽度 300px，1100px 以下曾缩至 240px，停靠后的输入文字为 13px；集市首屏右侧搜索列最大宽度为 520px。窄窗口中的导航文字与搜索空间共同限制了可读性。

| 场景 | 调整后的布局 |
| --- | --- |
| 961px 及以上导航 | 搜索高度 46px，弹性基准 360px，最小 280px、最大 400px；提示文字 15px |
| 电脑集市主搜索 | 高度 64px，右侧列最大 640px；1199px 以下最大 560px；输入文字 16px |
| 电脑停靠搜索 | 输入文字 15px，提交按钮显示“搜索”，宽度 64px |
| 960px 及以下 | 导航保留搜索图标和展开交互；主搜索保持既有 60px 高度 |
| 639px 及以下 | 主搜索保持既有 56px 高度，避免占用手机首屏 |

首页导航与集市搜索提示统一为“搜索编号、标题或区服”。继续使用原有滚动停靠和 FLIP 动画、减少动画偏好、Ctrl+K、Enter 提交、清空查询与 Escape 返回焦点逻辑，不另建搜索协议。

主要实现文件为用户端 `src/design-system.css`、`src/catalog.css`、`src/catalog-search.css`、`src/components/CatalogSearch.tsx` 与 `src/components/Layout.tsx`。

## 3 商品表单与分类

管理端账号资料顺序对齐会员端：发布类型 → 账号标题 → 区服、角色性别、VIP 等级 → 报价 → 自定义标签 → 账号介绍 → 私密交接资料 → 图片。管理专用的租赁标签和租赁交易分类保留在账号资料中。

### 3.1 出售交易分类

新建出售商品时，管理端不显示交易分类，也不发送 `category_id`。后端在创建事务中选取启用、适用于 `sale/all`、报价单位为空或包含 `account` 的分类，按 `sort_order,id` 稳定选择并持有共享锁。无可用分类时返回 422 `SALE_CATEGORY_UNAVAILABLE`，提示配置问题。

已存在商品继续发送并保留原 `category_id`，不因页面隐藏控件而重新分配分类；显式传入的无效分类仍被拒绝。只有新建出售的省略值使用默认规则。租赁商品仍显式选择兼容的交易分类。

### 3.2 租赁标签

时日／周月使用现有 `rental_category` 字段，与交易分类、具体报价时段分别保存。标签从旧审核操作区移到账号资料，并标明“审核或上架前必选”。草稿可暂不填写，保存草稿时可以保留已选标签；审核通过和直接上架必须有合法标签。

待审商品只更改标签时可以直接审核通过，由审核请求一并保存，不强迫先保存成草稿。标签的未保存变化参加离开提醒；其他内容修改仍遵守既有保存、内容版本和重新审核要求。租赁报价仍允许多个计价方式和自定义时段，不将标签当作金额换算规则。

## 4 管理列表与看板

商品编号独立显示在管理列表第一列，商品信息列继续展示封面、标题和属性；移动布局中编号也位于每条记录的首项。调整辅助文字和表格间距，原 9—11px 的相关文字提高至 12px。编辑操作栏回到正常文档流，避免覆盖报价编辑区。

看板将“待审核商品”“待审核昵称”提为独立卡片，分别跳转 `/reviews` 和 `/nickname-reviews`。说明文字明确为“当前全部待审核数量，不受 7／30 天选择影响”，两项不参加期间切换。

既有后端统计已经满足该口径：商品统计未删除且 `status='pending'` 的记录，与未筛选审核列表总数一致，不因分类停用或提交时间较早而遗漏；昵称统计 `status='pending'` 的申请，与昵称审核列表总数一致，包含停用会员仍待处理的申请。批准操作仍单独检查会员是否启用。本轮不为视觉突出而改写业务统计 SQL。

## 5 推荐加分数据与写入接口

新增迁移 `0020_product_recommendation_boost.sql`，不改写已发布的 0019 及以前迁移：

| 字段 | 定义 | 用途 |
| --- | --- | --- |
| `products.recommendation_boost` | integer，默认 0，约束 0—100 | 运营附加分 |
| `products.recommendation_version` | bigint，默认 1，约束大于 0 | 推荐设置的独立并发版本 |

管理员在商品列表或编辑页打开“推荐加分”弹窗。接口为 `PATCH /api/v1/admin/products/{id}/recommendation`，请求体为 `{ "boost": 20, "expected_version": 1 }`，成功返回 `data` 中的 `id`、`recommendation_boost` 和 `recommendation_version`。

| 条件 | 返回 |
| --- | --- |
| 未提供、非整数或范围外加分 | 422 `INVALID_RECOMMENDATION_BOOST` |
| 版本小于 1 | 422 `INVALID_VERSION` |
| 推荐版本已经改变 | 409 `RECOMMENDATION_VERSION_CONFLICT` |
| 商品不存在、已删除或已永久清理 | 404 |
| 操作者不再是启用管理员 | 拒绝写入 |

事务先对启用管理员持有共享锁，再锁定目标商品，核对推荐版本后更新两个推荐字段并写入审计。内容 `version`、`approved_version`、`status`、`published_at` 和 `updated_at` 均不变，独立设置不使已上架商品下架或触发重新审核。

媒体状态触发器只对“推荐版本改变，且所有非推荐字段完全相同”的写入提前返回；内容写入及原有无变化写入仍执行原保护。永久清理会归零加分并推进推荐版本。

推荐字段只进入管理端列表、详情和保存响应；公开、会员、共享商品投影不新增字段，审核内容快照显式去掉两个推荐字段。已有人工精选顺序接口仍独立保留。

### 5.1 冲突与未知结果

弹窗以打开时看到的推荐版本保存。409 或网络、服务异常等不能确认结果的情况会保留输入并锁定继续保存，要求点击“重新读取当前设置”。读取成功后展示数据库中的当前值，由管理员核对后决定是否再次修改。

该接口不使用 `request_id`。前端不在结果不明时自动使用新版本重放原输入；若第一次已提交，重读可以看到结果；若他人又修改，重读会显示对方的新值。请求进行中禁止关闭弹窗，避免在未获得结果时误以为操作取消。内容编辑页只刷新推荐字段，不重载或覆盖未保存的商品内容。

## 6 排序算法

加分在当前请求的可见、已筛选候选集合中计算，先参与完整集合排序，再分页。记运营加分为 `B`，范围 0—100。`H` 为未过期的自然热度：批次时间在最近 60 分钟内且不在未来；没有有效分数时为 0。

| 排序场景 | 主排序分数 |
| --- | --- |
| 热门 | `H + B` |
| 为你推荐，冷启动或个性化关闭 | `H + B` |
| 精选 | 有人工排名时 `max(1, 10001 - bigint(manual_rank)) + B`，否则为 `B` |
| 个性化，当前候选集至少有一个正 ItemCF 分数 | `100 × ItemCF + B` |
| 个性化，当前候选集无正 ItemCF 分数 | `(100 / 12) × (6 × 分类偏好 + 2 × 租售偏好 + 3 × 区服偏好 + 价格偏好) + B` |

判断 ItemCF 是否可用的是当前筛选后的候选集，避免其他分类存在关联商品却让本次候选集失去属性补齐。主分相同时保留原有完整次序：个性化仍比较原 ItemCF、属性匹配、未加分热度、上架时间及 ID；精选仍保留原人工排名、上架时间及 ID。人工排名表达式使用 bigint 并保留次序，兼容历史极端值。所有加分均为 0 时应保持原排序。

加分为加法，不保证某商品固定置顶。例如自然热度 150、加分 0 的商品仍高于自然热度 20、加分 100 的商品。修改后立即参与下一次列表读取，不改写自然热度或 ItemCF 物化表，也不等待刷新任务。最新上架、价格排序以及手动指定的首页轮播不受影响。

管理端 `GET /api/v1/admin/recommendations` 的榜单改为“当前热门排序”，与公开热门使用同一有效自然分加推荐分次序，包含没有自然快照的可见商品。`score` 保留原自然快照，`natural_score` 为有效自然分，`recommendation_boost` 为附加分，`hot_score` 为两者合计，`score_fresh` 表示快照是否有效。超过 60 分钟、未来时间及缺失快照的有效自然分均为 0。此榜单为非个性化热门，不声称展示每位会员的推荐结果，也不改写自然计算表。

榜单公式和计算示例使用已生效批次的 `applied_config`，不将刚保存而尚未重算的配置套到旧自然分上。商品编辑页合并图片详情、异步完整详情和推荐保存回调时分别核对推荐版本；较旧响应不能将已确认的新推荐版本和分数回退。

## 7 验证与发布边界

前端需覆盖桌面和手机宽度、停靠动画与减少动画模式、弹窗冲突/未知结果、表单分类省略和租赁标签路径。后端需验证加分边界、权限重核、并发版本、内容与媒体状态不变、公开字段隔离，以及筛选、分页和不同排序模式。

看板新增真实 HTTP 集成用例，比较 7／30 天及审核列表分页总数，并覆盖较早申请、停用分类/会员、拒绝和批准后的计数变化。写入联调只在既有隔离验收资源进行。

0020 需要依既有流程备份后迁移并核对结构。切回旧应用不会撤销已保存加分或数据库迁移，也不能当作数据恢复。最终发布须另行核对产物、双 API、静态资源与 GitHub 提交；152 业务站只做只读发布验收，5178 原型保持停用，8.140 生产环境保持既有只读边界。
